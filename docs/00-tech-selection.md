# 卡牌游戏 · 技术选型与架构决策（v1）

> 状态：已定稿 · 团队 3 人（1 前端 / 2 后端）· 目标 2-3 个月出可玩 demo

## 0. 已确认前提

| 项 | 结论 | 影响 |
|---|---|---|
| 平台优先级 | **微信/抖音小游戏是 v1 硬指标**，配套移动 App 也要支持 | 引擎必须选小游戏一等公民 |
| 变现 | **计划内购/道具付费** | 必须走企业主体 + **版号** + 微信虚拟支付进件 |
| 主体 | 已有企业或个体工商户主体 | 可选牌类/角色类类目，可申请版号 |
| 长期 | 效果好了再上 Steam | 需要跨平台导出能力（Cocos 支持 Windows/macOS 原生） |

## 1. 决策

**主方案：Cocos Creator 3.8 LTS + TypeScript**

- 唯一对微信/抖音小游戏提供官方一等支持的引擎（一键发布、分包、引擎插件、开放数据域）
- TypeScript 与前端工程师能力完全重合，也是 AI 辅助效率最高的语言
- 2026-01 COCOS 4 已全量 MIT 开源（引擎 + CLI），引擎存续风险显著降低，路线图明确 AI Native
- 一套工程可输出：小游戏（微信/抖音/支付宝/华为/OPPO/vivo）+ Android/iOS/HarmonyOS 原生 + Windows/macOS

**明确排除：**

- **Unreal**：与卡牌 + 小游戏需求完全错配（包体、2D/UI、学习成本）
- **Unity**：微信小游戏有官方方案但包体/启动耗时对小游戏是硬伤，卡牌游戏性价比极低
- **Godot**：本身优秀（2D/UI/Steam/零许可费），但小游戏链路依赖社区插件，不适合作为 v1 关键路径（详见 §5）

## 2. 分层架构（核心约束：引擎依赖必须压薄）

```
core/     纯 TypeScript，零引擎依赖
          · 规则状态机（回合/结算/优先级/连锁）
          · 确定性 RNG（seed 可复现）
          · 卡牌效果解释器（读数据 DSL）
          · 只输出事件流 events[]，不碰渲染
            │
client/   Cocos Creator 3.8 + TS
          · 订阅 events 播放表现（动画/音效/飘字）
          · UI / 资源 / 平台 SDK
            │
server/   Go
          · 账号 / 存档 / 排行榜 / 匹配 / 支付回调 / 风控
          · PvP 阶段：用 core 的 replay 做裁决校验
```

**为什么这样分**：core 可单测、可被 AI 大量生成、可在 Node 里跑 10 万局做平衡模拟、可在服务端复现对局。换引擎时重写的是表现层（2-4 周），不是游戏本身。

## 3. 技术栈清单

| 层 | 选型 | 备注 |
|---|---|---|
| 引擎 | Cocos Creator **3.8 LTS** | 不要用 4.0 起步（小游戏平台兼容仍在逐步发布） |
| 语言 | TypeScript（strict） | core 与 client 统一 |
| core 测试 | Vitest + golden replay | 固定 seed 跑 N 局，断言最终状态 hash |
| 数据 | YAML/JSON + JSON Schema + 自动生成 TS 类型 | 卡牌效果用 DSL，禁止 `switch(cardId)` 硬编码 |
| 服务端 | Go + WebSocket/HTTP | 账号、存档、排行榜、配置下发、支付校验 |
| 存储 | 关系库 + Redis | 按现有团队习惯定 |
| 资源 | CDN + 分包预下载；ASTC/WebP；中文字体子集化 | 首包只放 UI 骨架 + 首场景 |
| 配置 | 远程配置下发 | 数值/活动/文案不发版 |
| CI | lint + test + cocos build + 自动导出小游戏工程 | 每次 PR 产出可提审包 |

## 4. 内购/企业主体带来的合规动作（时间风险最高）

**版号是当前最大的时间风险，不是技术。** 立即并行启动：

| 事项 | 说明 | 建议启动时点 |
|---|---|---|
| 锁定游戏名称 + 主体 | 备案/版号提交后不可改 | 第 1 周 |
| 软著登记 | 版号与上架前置 | 第 1 周 |
| 版号申请 | 内购必需；周期数月级，可与开发并行 | 第 1-2 周 |
| 类目选择 | 卡牌大概率落 **牌类/角色类**（个人主体不可选） | 注册/提审前 |
| 微信虚拟支付进件 | 企业主体 + 版号后开通 | 版号批复后 |
| ICP 备案 / 小游戏备案 | 发布前置 | 第 1 周起并行 |
| 中宣部实名认证接入 | 开虚拟支付需自行接入 | 版号批复后 |
| 抖音侧资质 | 与微信类似，单独核实 | 第 1 周 |

**内容红线（牌类 + 内购审查更严）：**

- 抽卡/开箱**必须公示概率**
- 禁止任何类棋牌/赌博机制、禁止虚拟道具兑换现金/实物
- 广告占比、诱导分享等按平台规则控制

> 内购未批复前，用**体验版/灰度**完成开发与测试，不影响进度。

## 5. 备选方案：Godot（结论：不作为 v1 方案）

| 项 | 现实 |
|---|---|
| Web 导出 | 只支持 WebGL2 + Compatibility 渲染器；**C# 项目无法导出 Web** → 小游戏只能用 GDScript |
| wasm 体积 | 官方建议自行编译裁剪版导出模板才能显著减小；压缩后约原体积 1/4 |
| 小游戏适配 | 依赖社区插件 [godothub/godot-minigame](https://github.com/godothub/godot-minigame)（2026-03 建仓、165 star、Godot 4.4+、模板按版本分发） |
| 备选插件 | [godot-love-wechat](https://github.com/yuchenyang1994/godot-love-wechat)（400 star，但 2026-01 后无更新、无 License） |
| 平台 SDK | 登录/支付/广告/分享/开放数据域需自写 JS bridge，无官方 SDK，AI 帮助有限 |
| 额外投入 | 约 **1.5-3 人月**，且属不可控风险 |
| 适用场景 | 目标是 Steam/PC/App 优先，或团队有能力做引擎级工作 |

**止损机制**：若未来仍要评估 Godot，先做 2 周 Spike（导出→真机跑通→首包 ≤4MB→冷启 <3s→`wx.login`→激励视频→分享+好友榜→引擎升一次版本验证维护成本），任一项卡住超 3 天即放弃。

## 6. 前两周执行清单

**Week 0（3-5 天）**

- [ ] Cocos Creator 3.8 LTS 安装 + 空项目导出微信小游戏，**真机跑通**
- [ ] 测出真实首包体积与冷启动耗时（目标：首包 ≤4MB、冷启 <3s）
- [ ] 合规动作全部启动（§4 表格）
- [ ] 仓库初始化：monorepo（`core/` `client/` `server/` `data/` `docs/`）+ CI + `AGENTS.md`

**Week 1-2（唯一不可妥协的节点）**

- [ ] `core` 规则状态机 + 效果 DSL + 数据管线（YAML→TS 类型）
- [ ] 单机一局能完整打完（占位美术，色块/纯文本均可）
- [ ] Vitest + golden replay 跑通
- [ ] 卡牌 20 张、1 个 boss、1 个关卡闭环

> **W2 结束必须能"完整打一局"**。卡牌项目最典型的死法是机制一直讨论、闭环一直没出来。

## 7. 人力分工

| 角色 | 负责 | 关键提醒 |
|---|---|---|
| 前端（1 人） | Cocos 工程、UI、动画表现、小游戏/App 平台 SDK | 平台接入是 v1 最容易低估的工作量 |
| 后端 A（1 人） | **core 规则引擎 + 数据管线 + 平衡模拟器** | 这是卡牌项目最关键岗位，不要由最忙的人兼 |
| 后端 B（1 人） | Go 服务端、账号/存档/排行榜、支付与登录校验、埋点 | 版号未批复前先做体验版链路 |

## 8. AI 辅助的边界

| 让 AI 干 | 别让 AI 干 |
|---|---|
| core 规则/效果解释器（有测试兜底） | 引擎版本相关的平台适配代码 |
| 数据 schema、Excel→JSON 导出脚本 | 微信/抖音 SDK 接入（幻觉代价高） |
| 单元测试 + golden replay | 构建/分包/原生工程配置 |
| 平衡模拟器与数值报表 | 包体与性能调优的最终判断 |
| UI 骨架、文档、ADR | 合规/版号相关决策 |

配套：`AGENTS.md`（架构约定 + 禁用 API 清单）+ `docs/adr/` + CI 自动构建。

## 9. 风险清单

| 风险 | 等级 | 对策 |
|---|---|---|
| 版号周期长（数月） | **高** | 第 1 周启动；内购功能延后到批复后 |
| 内容量做不完（卡池/平衡） | **高** | 数据驱动 + DSL；W2 必须闭环；平衡靠模拟器 |
| 小游戏包体超限 | 中 | 首包只放骨架；资源 CDN + 分包；字体子集化 |
| 平台 SDK 接入耗时 | 中 | 第 1 周就打通登录/广告；抽平台抽象层 |
| 引擎版本迁移 | 中 | 逻辑与引擎解耦；锁 3.8 LTS |
| 人才/资料稀缺 | 低 | 选 Cocos 正是因为它资料与人才池最大 |
